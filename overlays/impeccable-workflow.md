# Portable design workflow

SUPERBROWKY adaptation v2 of selected Impeccable 4.9.2 guidance. Upstream:
[pinned source](https://github.com/pbakaus/impeccable/tree/d41d9860b0094dcb68030657da63461212835aaa).
This manual workflow replaces engine-dependent playbooks. No engine, browser
injection, automatic detector, hook, generated agent or hidden context writer
is part of the package.

## New work and refinement

1. Preserve the outcome, exact source/version, latest corrections, prior
   authorization and remaining acceptance checks. Read the relevant context
   mapped by `PROJECT.md`, current code, actual assets and accepted decisions.
2. Select Operate, Read, Persuade or Experience for the surface. Reuse the
   established system. Missing Markdown is not evidence of a blank project.
3. For a clear brief choose a fitting implementation. Resolve reversible
   spacing, hierarchy and layout choices directly. Ask about a new identity,
   conflicting direction or unavailable required asset only when it matters.
4. Read `reference/craft-floor.md` and the task-specific craft guide. Implement
   within the authorized surface; preserve factual copy and brand assets.
5. Follow craft owner → builder → owner verification → independent review.
   Use only roles available in the active catalog; never imitate a missing
   specialist or describe your own second pass as independent review.

## Critique and audit

Inspect the exact artifact and its reference. Use
`reference/critique-rubric.md` for usability questions, with the selected mode
and actual audience. Return at most five prioritized findings, each with
evidence, user impact and a concrete correction or check. Do not invent scores
or infer user behavior from a screenshot.

Use `a11y-audit`, `psi-optimize`, or `meta-audit` only for relevant evidence and
only when actually available. Never label a skipped detector or unavailable
browser check as passed. Read-only review does not save a report or edit files
unless that write is part of the user's request.

## Motion and detail

Use the current platform and design system. Check type hierarchy and actual
glyphs, spacing, text overflow and representative content. For material motion,
read `emil-design-eng`; check reduced motion, interruption and relevant input
methods. Do not add an animation library just to follow a reference.

## Final verification and polish

Build fully, inspect the relevant rendered states and sizes together, fix
confirmed defects in one batch, then verify the changed artifact again. Stop
unproductive polishing. Check the complete path to the intended user action,
including relevant loading, empty, failure and success states. Static images
do not prove keyboard handling, responsive reflow or completion of a purchase.

Use authorized rendering tools. Browser automation requires explicit visual-QA
authorization; existing renders can provide narrower static evidence. Report
local, preview, deployed and live-verified states separately. Unverified
criteria remain `PARTIAL`, not a simulated engine pass.

## Context documentation

When context authoring is requested, preserve the project's existing canonical
files, schema, accepted decisions and surface mapping. Draft only what evidence
supports, label assumptions, and keep product/design acceptance human-owned.
Do not create competing `.impeccable` context, sidecars, reports or runtime
receipts. A narrow refinement can proceed on existing project evidence; offer
broader context work afterward if useful.
